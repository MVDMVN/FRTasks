# Формат менторства — ОБЯЗАТЕЛЬНО СОБЛЮДАТЬ

Ты — мой ментор-практик, не лектор. Работаем по циклу:

1. Даёшь мне одну конкретную задачу по текущей теме.
2. Я пытаюсь решить сам 20-30 минут — гуглю, экспериментирую, читаю доки.
3. Ты НЕ подсказываешь и не встреваешь, пока я сам не скажу "застрял" или не
   покажу решение.
4. Если я застрял — даёшь наводящий вопрос сначала, а не готовый ответ. Полное
   решение — только если это не помогает.
5. Если решил сам — коротко разбираем: что можно было сделать чище/идиоматичнее,
   какие грабли обошёл или не обошёл.
6. Двигаемся дальше к следующей задаче по плану ниже.

Никаких лекций до задачи. Никаких длинных теоретических вступлений. Теория —
только по запросу или как короткий разбор после того как я уже попробовал.

**Рабочий процесс между Claude Code и чатом:** в Claude Code — заготовки файлов,
написание кода, git. В чате — ревью кода по этому файлу и разбор. После каждой
решённой задачи — обновляю этот файл (раздел "Текущий статус"), чтобы в чате

# Пройдено

**Задача 1 — `01-js/01-orders-groupby/`** (сводка заказов по клиентам,
map/filter/reduce). Решена, тесты зелёные.

Ключевой урок — механика `reduce`:

- без `initialValue` вторым аргументом `reduce` берёт первый элемент массива как
  стартовый `acc` и начинает перебор со второго — не пустой объект, как можно
  было по ошибке предположить
- если колбэк с блочным телом `{ }` не делает явный `return`, он возвращает
  `undefined` — и это `undefined` подставляется как `acc` на следующей итерации
- решение через мутацию внешней переменной вместо `return acc` технически может
  "работать" по побочному эффекту, но это не идиоматичный `reduce`, а
  замаскированный `forEach`

# Пройдено (продолжение)

**Задача 2 — `01-js/02-debounce/`** (замыкания). Решена, тесты зелёные.

Ключевой урок — `fn` vs `fn(...args)` в колбэке таймера:

- `setTimeout` ждёт ссылку на функцию, которую вызовет сам, когда сработает
  таймер
- `fn(...args)` — это немедленный вызов; в `setTimeout` улетает не функция,
  а то, что `fn` вернула (обычно `undefined`)
- решение — обернуть в стрелочную функцию: `setTimeout(() => fn(...args), delay)`

Ещё поймал по красным тестам: забыл присвоить `timerId = setTimeout(...)` —
без этого `clearTimeout` было нечего отменять, старый таймер продолжал висеть.

**Задача 3 — `01-js/03-retry/`** (async/await, промисы). Тесты зелёные, но
НЕ решена самостоятельно — код от ментора, скопирован как есть. Задача
оказалась перегружена: сразу 3 новые идеи одним куском (промисификация
setTimeout через sleep, throw vs return для отклонения промиса, границы
цикла по retries). Вызвала сильную фрустрацию, понимания по факту нет —
тему async/await нужно будет вернуть позже отдельными мелкими шагами.

Ключевой урок:

- `async function` всегда возвращает Promise, даже `return 'x'` снаружи —
  это `Promise { 'x' }`, доставать значение — только через `await`
- чтобы промис отклонился (reject), из async-функции нужно `throw`,
  а не `return err` — `return` всегда резолвит
- `setTimeout` колбэковый, `await` умеет ждать только промisы — оборачивать
  через `new Promise((resolve) => setTimeout(resolve, ms))`

**Задача 5 — `01-js/05-toggle-item/`** (иммутабельное обновление массива —
map + spread, паттерн из React setState). Решена самостоятельно, тесты
зелёные. Выбрана специально как что-то знакомое по практике React, а не
новая тема с нуля — сработало, задача далась нормально.

Мелкие правки по ревью, оба принял: `===` вместо `==`, `return item` без
лишнего spread для неизменённых элементов.

Разобрали отдельно механику spread: `{ ...item, done: true }` — это не
особая логика spread, а обычное правило object literal "последний
дублирующийся ключ побеждает". `...item` разворачивается как обычные
присвоения полей, а `done: true` ниже просто перезаписывает то, что
раскрыл spread. Источник путаницы — статьи про spread (напр. Кантор,
learn.javascript.ru) фокусируются на "как скопировать", а не на этом
пересечении с поведением object literal.
